# Zinn for Codex

Inspect local Zinn tasks alongside a Codex desktop conversation, move reviewed tasks and edit their title, description and priority. The plugin provides manual task lookup, full descriptions, comments, relation navigation and observed task references from the current chat. Optional hooks supply execution identity for direct Zinn commands.

**Zinn for Codex 0.1.0** is Experimental.

## Requirements

- Codex desktop with MCP Apps for the inspector, and the Codex CLI (`codex`) for installation. See [Compatibility](#compatibility) for the verified desktop setup.
- Node.js 24.15.0 or newer and [Zinn CLI](/docs/installation) 0.45.0 or newer on the app's `PATH`.

## Install from GitHub

Add [Zinn's plugin catalog](https://github.com/yethranayeh/zinn/tree/codex-marketplace) as a marketplace in Codex, then install the plugin.

```sh
codex plugin marketplace add yethranayeh/zinn --ref codex-marketplace
codex plugin add zinn@zinn
```

Open a new chat in Codex desktop. When Codex asks you to review the plugin's hook definitions, approve the hooks you want to use. Manual task lookup works with hooks disabled. You can configure observation and identity independently under [Hook settings](#hook-settings).

## Inspect tasks

The inspector finds your Zinn database automatically, usually in `~/.zinn`. If you're new to Zinn, [create your first project and task](/docs/quick-start) so you have a task to look up.

In a chat, open a new side tab, choose **More tools**, then **Plugins and MCPs**, and open **Zinn task inspector**. Launcher labels can vary by Codex version.

Enter a task key from your database, such as `APP-1`. Task descriptions and comments are displayed as literal text, preserving line breaks. Select a relation to open the related task. **Refresh** reads the selected task and current-chat references again.

Opening a task through lookup, an observed reference or a relation remembers its key for the current chat and selected database directory. Reopening the panel reads that task's current contents. A missing task keeps its selected key so you can retry or open another task. An explicit task key supplied when opening the panel takes precedence over the remembered selection.

Selection is remembered only when the host identifies the chat unambiguously. Manual lookup remains available otherwise. A failed selection save leaves task inspection available and reports that the selection could not be remembered. Invalid lookup input and task-read errors preserve the previously remembered key.

For an active task, choose a destination and select **Move to…**. The initial destination is the project's first column with the `done` category, or the task's current column when the project has none. The move uses the inspector's selected database and the task's own project. It follows ordinary `zinn task move` behavior and refreshes the task afterward. Moving to the current column leaves it unchanged. Archived tasks remain available for inspection.

Panel moves and field saves record your normal CLI human identity, with inherited agent, model, effort, client and conversation declarations cleared. Their `actor_client` identifies the CLI and `zinn-codex/0.1.0`. Use `zinn activity list --client zinn-codex` to select that history. Read commands retain any inherited [client chain](/docs/cli/identity#client-chains) and append the plugin token. Codex's tool permission settings apply. A move is submitted only by the explicit button action and is not automatically retried after a failure.

### Edit task fields

For an active task, select **Edit**, change its title, description or priority, then select **Save**. Saving sends only changed fields through `zinn task edit`, together with their values when you opened Edit, and reads the task again afterward. **None** clears the priority. An empty description clears its stored value. Priority choices come from the configured CLI. If loading them fails, title and description remain editable while priority stays unchanged. Use **Retry priorities** to try loading the choices again.

There is no autosave. **Cancel**, **Refresh** or opening another task requires explicit discard when the draft has changes. Keep the panel open while you work: drafts stay in panel memory, while remembered selection stores only the task key.

Validation, permission and write failures keep the draft. If the host cannot confirm whether a save completed, the panel reads the current task without replaying the write. Review the refreshed task before retrying **Save**. If the follow-up read fails, the draft remains available for explicit recovery.

If another client changes a field you edited, Save refuses the whole edit and names the conflicting fields. Your draft stays open while the panel reads the current task. Select **Review conflicts**, then choose **Keep my draft** or **Use saved value** for each conflicting field. **Apply choices** updates the draft without writing. Select **Save** when ready. The next save checks the reviewed saved values, so another intervening change refuses again. If reading the current task fails, **Review conflicts** retries the read. There is no automatic retry or merge. Changes to fields you left untouched survive and do not block Save. A refused save or a save that changes no stored values adds no activity.

### Current-chat references

Observed references come from supported direct CLI calls, task keys in agent dispatches and completed replies. A reference is an observation, rather than a task assignment or proof that the task changed. References refresh every five seconds while the panel is visible, keeping the selected task open. Task details are re-read when opened or refreshed.

References with a relative `ZINN_DIR` are recorded when the command's working directory can be established.

Each request uses the host's current chat metadata. Manual lookup remains available when that metadata is absent or conflicting. Completed-reply keys are checked against the selected store. A missing key is retained as a warning when its project prefix is represented by tasks in that store.

Panel reads can wait for another process or an automatic upgrade to finish. Cancelling a request or closing the backend stops its CLI child. Periodic refresh waits for the pending reference read to complete.

## Optional configuration

The plugin resolves the database using the CLI's settings from your home directory, including any `ZINN_DIR` inherited by Codex. Agent commands use their own working directory and environment, so they can select a different database. Restart Codex after changing its environment or storage settings.

To point the inspector and its reference checks at a specific database, set `store` to the absolute path to its Zinn data directory in `~/.zinn/integrations/codex.json`.

```json
{
	"store": "/absolute/path/to/.zinn"
}
```

If the desktop app cannot find `zinn`, you can use the executable's absolute path. The `cli` array can also include fixed arguments.

```json
{
	"cli": ["/absolute/path/to/zinn"]
}
```

The settings file stays in your home directory even when `ZINN_DIR` points elsewhere. The plugin also accepts the older `~/.config/zinn/codex.json` path when `~/.zinn/integrations/codex.json` is absent. To use a different file, set `ZINN_CODEX_CONFIG` to its absolute path in Codex's environment. The plugin reads one file. An explicitly selected file must exist, and a configuration error stops the plugin from loading.

## Hook settings

The configuration accepts these options:

| Option          | Default                     | Behavior                                                                            |
| --------------- | --------------------------- | ----------------------------------------------------------------------------------- |
| `store`         | CLI selection               | Optional absolute Zinn data directory for inspection and reply verification.        |
| `cli`           | `["zinn"]`                  | Executable and fixed arguments used for reads and requested panel changes.          |
| `dataDirectory` | `~/.local/share/zinn-codex` | Absolute directory for local integration state, outside the Zinn data directory.    |
| `observe`       | `true`                      | Record task references for the current-chat list.                                   |
| `identity`      | `true`                      | Supply the callback's agent profile and model to supported direct commands.         |
| `captureEffort` | `false`                     | Read exact execution metadata from the callback's transcript file to supply effort. |

Use absolute paths in JSON. The default integration data path is resolved from your home directory.

Identity capture handles one literal direct `zinn` command, or the configured CLI invocation. It appends `zinn-codex/0.1.0` after any inherited [client chain](/docs/cli/identity#client-chains). It leaves compound shell commands and shell expansions unchanged. Explicit `ZINN_AGENT`, `ZINN_MODEL`, `ZINN_EFFORT` and `ZINN_CLIENT` assignments in that command take precedence. Unknown values clear inherited hook attribution for that command. Codex requires a `PreToolUse` allow response to accept rewritten input. The plugin uses that response and does not register a `PermissionRequest` hook. Review its definitions before trusting them. See [Codex hooks](https://learn.chatgpt.com/docs/hooks). Zinn records activity only when the CLI operation makes a change.

With `captureEffort: true`, effort is supplied only when the transcript's thread, turn and model match the callback and exactly one matching turn context exists. Missing, partial, oversized or ambiguous metadata leaves effort unknown. Duplicate contexts can occur after compaction. See [CLI actor identity](/docs/cli/identity#who-am-i) for the recorded fields.

To stop reference recording and identity capture, set both `observe` and `identity` to `false`. To keep recording references and disable identity capture, set only `identity` to `false`. These settings take effect on the next hook invocation. Previously recorded references remain available until their files are removed.

These hook settings do not disable the panel's remembered selection.

Optional reply and dispatch verification shares a short deadline across CLI compatibility, `info --json` and task lookup. It proceeds when the schema is current. Unavailable completed-reply verification is recorded separately. Execution identity remains independent. The schema check is best effort because another client can replace or restore the database before the following read.

## Update, disable and remove

For a GitHub installation, close the inspector, refresh the marketplace and install the current plugin version:

```sh
codex plugin marketplace upgrade zinn
codex plugin add zinn@zinn
```

Restart Codex and start a new chat to use the updated plugin. Review changed hook definitions again when requested.

Disable **Zinn** in the Plugins browser to stop loading it. To uninstall the plugin and remove its marketplace registration, close the inspector and run:

```sh
codex plugin remove zinn@zinn
codex plugin marketplace remove zinn
```

Your Zinn database, configuration, reference files and selection records remain under your control. Remove the dedicated integration data directory separately if you want to clear its metadata.

To roll back to an earlier version or reinstall a specific release, remove the plugin and marketplace registration as shown above, then [install its archive](#install-the-archive). Restart Codex and check lookup, editing and hook trust again. Database compatibility continues to follow the installed CLI and its ordinary [backup and restore rules](/docs/data).

## Install the archive

The versioned archive contains the plugin and its marketplace catalog. Use it to install a specific release from disk.

Download the [0.1.0 archive](https://raw.githubusercontent.com/yethranayeh/zinn/55d9997f1f58937c8e7239581d07cd5b3db48c13/downloads/zinn-codex-0.1.0.tar.gz) and its [SHA-256 checksum file](https://raw.githubusercontent.com/yethranayeh/zinn/55d9997f1f58937c8e7239581d07cd5b3db48c13/downloads/zinn-codex-0.1.0.tar.gz.sha256) into the same directory. From that directory on macOS, verify the checksum before extracting:

```sh
shasum -a 256 -c zinn-codex-0.1.0.tar.gz.sha256
```

After the check succeeds, extract into a directory without an existing `zinn-codex` folder, register the extracted marketplace and install Zinn:

```sh
tar -xzf zinn-codex-0.1.0.tar.gz
codex plugin marketplace add ./zinn-codex
codex plugin add zinn@zinn
```

Keep the extracted `zinn-codex` directory available as the marketplace source. Open a new chat and review the hooks Codex prompts you to approve.

For development, see the [source build instructions](https://github.com/yethranayeh/zinn/tree/main/integrations/codex#development).

## Troubleshooting

If the inspector fails to start, check that Codex can find `node` and `zinn` and that both meet the version requirements. A `-dev` Zinn CLI build must have a numeric version newer than `0.45.0`. If you use [optional configuration](#optional-configuration), check the configured paths. Run `zinn info` from your home directory with the same environment and CLI executable to check which database Zinn finds.

For an empty recent list, check hook trust and `observe`, then mention a real task key in a completed reply or run a direct CLI lookup. Failed verification is reported separately from a missing task. A newly created task becomes available on the next refresh.

If saving fails, keep the panel open, read its error and review the current task before retrying. A retained draft is not proof that the first save failed to reach the database.

If an updated inspector still shows its previous controls, close the inspector tab and reopen it from **More tools**. **Refresh** rereads task data without reloading the interface.

## Compatibility

Zinn for Codex 0.1.0 was verified in Codex desktop on macOS. Backend tests run on macOS, Linux and Windows. Native panel rendering and hook behavior require separate verification on other desktop setups.

Native field editing and conflict review were verified on macOS `15.7.4` arm64 with desktop app `26.1111.21308` build `27194`, `codex-cli 0.169.0-alpha.11.1`, Node `26.13.0` and published Zinn CLI `0.45.0`. The check covered refusal after an external edit, retaining a draft, explicit per-field review, another refusal after a later edit and a successful human-attributed save. The same plugin build passed isolated backend checks for startup, exact inspector assets, disable, removal, reinstall and rollback to a retained candidate. Identity command rewriting uses Unix shell syntax.

When the host or plugin version changes, recheck native opening, hook trust, references, human Move and Save attribution, selection after reopen, update, disable, removal and rollback before relying on that combination. Zinn maintains the plugin and its compatibility fixes.

Report problems through [GitHub Issues](https://github.com/yethranayeh/zinn/issues). Include the plugin version and archive checksum, Codex desktop app and CLI versions, Node and Zinn CLI versions, operating system, relevant component settings, expected behavior and a synthetic reproduction. Keep database files, transcripts, reference records and private task text out of the report.

## Local data and privacy

The inspector and hook verification read the database through the installed Zinn CLI. If the database needs an upgrade, the CLI [backs it up before upgrading](/docs/data#upgrade-a-database). Reads on a current database leave task data and activity unchanged.

The observer writes task keys, their source, selected-store paths, chat IDs and timestamps. It processes shell text, dispatch text and completed replies in memory to find those keys. The reference files contain this metadata rather than command arguments, prompts, replies or task contents. Effort capture processes the callback's transcript file in memory and retains no transcript copy.

Each chat has at most 1,024 reference records of at most 16 KiB each. Reaching that limit is reported by the inspector. Reference data persists across plugin upgrades and has no automatic expiry. Disable observation and remove the integration's hashed chat subdirectories to clear only reference records. With the default dedicated directory, remove `~/.local/share/zinn-codex` to clear all local integration state.

The panel keeps one selection record per chat and canonical selected-store path in `dataDirectory/selections`. Each record contains only a format version and task key. Its filename hashes the chat and store scope. Task contents and drafts are fetched or held in memory rather than saved in these records. Selection state survives normal app restarts and plugin upgrades, has no automatic expiry and remains after uninstall. Stop the plugin and remove only its `selections` subdirectory to clear remembered selections while keeping reference records. Restoring or replacing a database at the same path keeps the same selection scope and reads the task key against the current database.

The plugin uses local STDIO and has no hosted server. Task data returned through the native panel passes through Codex. Your host's data-handling settings and policies apply. Keep database files, transcripts and reference files out of public support reports.
