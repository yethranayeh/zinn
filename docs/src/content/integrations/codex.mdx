# Zinn for Codex

Inspect local Zinn tasks alongside a Codex desktop conversation, move reviewed tasks and edit their title, description and priority. The plugin provides manual task lookup, full descriptions, comments, relation navigation and observed task references from the current chat. Optional hooks supply execution identity for direct Zinn commands.

This guide covers the Experimental **0.1.0** candidate. Its versioned archive contains a self-contained local marketplace, runtime JavaScript, inspector assets and dependency licenses.

## Requirements

- Codex desktop on macOS with local plugin marketplaces, lifecycle hooks and MCP Apps conversation panels. See [Compatibility](#compatibility) for the candidate's verification status.
- Node.js 24.15.0 or newer and Zinn CLI 0.45.0 or newer on the app's `PATH`.
- An existing Zinn database that the installed CLI can read.

Follow [CLI installation](/docs/installation) to install Zinn. The archive runs with Node and the installed CLI. Bun, Astro, Tailwind and the source checkout are build tools.

A `-dev` CLI build must have a numeric version newer than `0.45.0`.

The inspector and hook verification use ordinary CLI read commands with the host user's permissions. Normal database compatibility rules apply, including backups and automatic upgrades when the CLI opens an older database. Current-schema reads leave task data and activity unchanged. SQLite manages its normal WAL coordination files.

Configured CLI executables are trusted local programs. The hook writes its own reference files.

## Select the database

Default-store setup needs no plugin configuration file. The plugin runs `zinn info --json` from your home directory to resolve the database location. It honors `ZINN_DIR` inherited by Codex and the CLI's settings in that context, including global storage selection. Without an override, Zinn uses `~/.zinn`.

The inspector keeps that selected directory until it restarts. It checks CLI compatibility with `--version` before reading tasks. Restart Codex after changing its environment or storage settings.

Agent commands use their own working directory, CLI settings and `ZINN_DIR`. Their selected database can differ from the inspector's. Set `ZINN_DIR` in Codex's environment when inspection should use a custom directory.

For plugin-specific options, create the optional `~/.zinn/integrations/codex.json`. This location stays in your home directory even when `ZINN_DIR` selects a different store. An explicit `store` selects inspection and reference verification independently of agent commands:

```json
{
	"store": "/absolute/path/to/.zinn"
}
```

An options file can omit `store` and use ordinary discovery. To select another file, set `ZINN_CODEX_CONFIG` in Codex's environment to its absolute path. The plugin reads that file exclusively. Otherwise, it reads `~/.zinn/integrations/codex.json`, falling back to an existing `~/.config/zinn/codex.json` only when the new path is absent.

Only one options file is read. Files are never merged or moved automatically. Missing implicit files use the defaults. An explicitly selected file must exist, and any selected file must be readable and valid. A configuration error stops loading without trying another file.

If the desktop app cannot find `zinn`, use the executable's absolute path:

```json
{
	"cli": ["/absolute/path/to/zinn"]
}
```

`cli` is an array containing the executable and any fixed arguments. The app must also be able to find `node` on its `PATH`.

## Install the archive

Place `zinn-codex-0.1.0.tar.gz` and `zinn-codex-0.1.0.tar.gz.sha256` from the same candidate together in a directory you control. From that directory on macOS, verify the checksum before extracting:

```sh
shasum -a 256 -c zinn-codex-0.1.0.tar.gz.sha256
```

Continue only when the checksum check succeeds. Then extract and register the marketplace:

```sh
tar -xzf zinn-codex-0.1.0.tar.gz
codex plugin marketplace add ./zinn-codex
```

Keep the extracted `zinn-codex` directory available as the marketplace source. Codex manages its installed copy.

Open Codex's Plugins browser, choose the **Zinn** marketplace and install **Zinn**. Review the plugin's hook definitions and approve the components you want to use when Codex requests it, then start a new chat. Installing or enabling a plugin does not automatically trust its hooks. You can configure observation and identity independently under [Hook settings](#hook-settings). See [OpenAI's plugin setup guide](https://developers.openai.com/plugins/build/plugins).

For a consumer check before selecting your own database, replace `/absolute/path/to/zinn-sample` below with a new directory and seed a synthetic project there:

```sh
mkdir -p /absolute/path/to/zinn-sample
ZINN_DIR=/absolute/path/to/zinn-sample zinn project create APP
ZINN_DIR=/absolute/path/to/zinn-sample zinn task create APP --title "Review the example" --description "Synthetic setup task"
```

Set the optional plugin `store` to that absolute directory, restart the inspector and look up `APP-1`. You can test Move, Edit, Save and reopen behavior there before selecting your working database. Agent commands need their own matching `ZINN_DIR` to use the sample.

### Build from source

To create the candidate archive from a Zinn source checkout:

```sh
bun install --frozen-lockfile
bun install --cwd integrations/codex --frozen-lockfile
bun run codex:package
```

The archive and checksum are written to `integrations/codex/release-dist`. Use the archive installation steps above. Building does not install the plugin.

## Inspect tasks

In a chat, open a new side tab, choose **More tools**, then **Plugins and MCPs**, and open **Zinn task inspector**. Launcher labels can vary by Codex version.

Enter a task key from your database, such as `APP-1`. Task descriptions and comments are displayed as literal text, preserving line breaks. Select a relation to open the related task. **Refresh** reads the selected task and current-chat references again.

Opening a task through lookup, an observed reference or a relation remembers its key for the current chat and selected database directory. Reopening the panel reads that task's current contents. A missing task keeps its selected key so you can retry or open another task. An explicit task key supplied when opening the panel takes precedence over the remembered selection.

Selection is remembered only when the host identifies the chat unambiguously. Manual lookup remains available otherwise. A failed selection save leaves task inspection available and reports that the selection could not be remembered. Invalid lookup input and task-read errors preserve the previously remembered key.

For an active task, choose a destination and select **Move to…**. The initial destination is the project's first column with the `done` category, or the task's current column when the project has none. The move uses the inspector's selected database and the task's own project. It follows ordinary `zinn task move` behavior and refreshes the task afterward. Moving to the current column leaves it unchanged. Archived tasks remain available for inspection.

Panel moves and field saves record your normal CLI human identity, with inherited agent, model, effort, client and conversation declarations cleared. Their `actor_client` identifies the CLI and `zinn-codex/0.1.0`. Use `zinn activity list --client zinn-codex` to select that history. Read commands retain any inherited [client chain](/docs/cli#client-chains) and append the plugin token. Codex's tool permission settings apply. A move is submitted only by the explicit button action and is not automatically retried after a failure.

### Edit task fields

For an active task, select **Edit**, change its title, description or priority, then select **Save**. Saving sends only changed fields through `zinn task edit`, together with their values when you opened Edit, and reads the task again afterward. **None** clears the priority. An empty description clears its stored value. Priority choices come from the configured CLI. If loading them fails, title and description remain editable while priority stays unchanged. Use **Retry priorities** to try loading the choices again.

There is no autosave. **Cancel**, **Refresh** or opening another task requires explicit discard when the draft has changes. Keep the panel open while you work: drafts stay in panel memory, while remembered selection stores only the task key.

Validation, permission and write failures keep the draft. If the host cannot confirm whether a save completed, the panel reads the current task without replaying the write. Review the refreshed task before retrying **Save**. If the follow-up read fails, the draft remains available for explicit recovery.

If another client changes a field you edited, Save refuses the whole edit and names the conflicting fields. Your draft stays open while the panel reads the current task for comparison. There is no automatic retry or merge. To start from the current values, cancel and explicitly discard the draft, then reopen Edit. Changes to fields you left untouched survive and do not block Save. A refused save or a save that changes no stored values adds no activity.

### Current-chat references

Observed references come from supported direct CLI calls, task keys in agent dispatches and completed replies. A reference is an observation, rather than a task assignment or proof that the task changed. References refresh every five seconds while the panel is visible, keeping the selected task open. Task details are re-read when opened or refreshed.

References with a relative `ZINN_DIR` are recorded when the command's working directory can be established.

Each request uses the host's current chat metadata. Manual lookup remains available when that metadata is absent or conflicting. Completed-reply keys are checked against the selected store. A missing key is retained as a warning when its project prefix is represented by tasks in that store.

Panel reads can wait for another process or an automatic upgrade to finish. Cancelling a request or closing the backend stops its CLI child. Periodic refresh waits for the pending reference read to complete.

## Hook settings

The configuration accepts these options:

| Option          | Default                     | Behavior                                                                            |
| --------------- | --------------------------- | ----------------------------------------------------------------------------------- |
| `store`         | CLI selection               | Optional absolute Zinn data directory for inspection and reply verification.        |
| `cli`           | `["zinn"]`                  | Executable and fixed arguments used for reads and requested panel changes.          |
| `dataDirectory` | `~/.local/share/zinn-codex` | Absolute directory for local integration state, outside the Zinn data directory.    |
| `observe`       | `true`                      | Record task references for the current-chat list.                                   |
| `identity`      | `true`                      | Supply the callback's agent profile and model to supported direct commands.         |
| `captureEffort` | `false`                     | Read exact execution metadata from the callback's transcript file to supply effort. |

Use absolute paths in JSON. The default data path is resolved from the user's home directory. `ZINN_CODEX_CONFIG` can select a different absolute configuration-file path when it is set in the host's environment.

Identity capture handles one literal direct `zinn` command, or the configured CLI invocation. It appends `zinn-codex/0.1.0` after any inherited [client chain](/docs/cli#client-chains). It leaves compound shell commands and shell expansions unchanged. Explicit `ZINN_AGENT`, `ZINN_MODEL`, `ZINN_EFFORT` and `ZINN_CLIENT` assignments in that command take precedence. Unknown values clear inherited hook attribution for that command. Codex requires a `PreToolUse` allow response to accept rewritten input. The plugin uses that response and does not register a `PermissionRequest` hook. Review its definitions before trusting them. See [Codex hooks](https://learn.chatgpt.com/docs/hooks). Zinn records activity only when the CLI operation makes a change.

With `captureEffort: true`, effort is supplied only when the transcript's thread, turn and model match the callback and exactly one matching turn context exists. Missing, partial, oversized or ambiguous metadata leaves effort unknown. Duplicate contexts can occur after compaction. See [CLI actor identity](/docs/cli#who-am-i) for the recorded fields.

To stop reference recording and identity capture, set both `observe` and `identity` to `false`. To keep recording references and disable identity capture, set only `identity` to `false`. These settings take effect on the next hook invocation. Previously recorded references remain available until their files are removed.

These hook settings do not disable the panel's remembered selection.

Optional reply and dispatch verification shares a short deadline across CLI compatibility, `info --json` and task lookup. It proceeds when the schema is current. Unavailable completed-reply verification is recorded separately. Execution identity remains independent. The schema check is best effort because another client can replace or restore the database before the following read.

## Local data and privacy

The observer writes task keys, their source, selected-store paths, chat IDs and timestamps. It processes shell text, dispatch text and completed replies in memory to find those keys. The reference files contain this metadata rather than command arguments, prompts, replies or task contents. Effort capture processes the callback's transcript file in memory and retains no transcript copy.

Each chat has at most 1,024 reference records of at most 16 KiB each. Reaching that limit is reported by the inspector. Reference data persists across plugin upgrades and has no automatic expiry. Disable observation and remove the integration's hashed chat subdirectories to clear only reference records. With the default dedicated directory, remove `~/.local/share/zinn-codex` to clear all local integration state.

The panel keeps one selection record per chat and canonical selected-store path in `dataDirectory/selections`. Each record contains only a format version and task key. Its filename hashes the chat and store scope. Task contents and drafts are fetched or held in memory rather than saved in these records. Selection state survives normal app restarts and plugin upgrades, has no automatic expiry and remains after uninstall. Stop the plugin and remove only its `selections` subdirectory to clear remembered selections while keeping reference records. Restoring or replacing a database at the same path keeps the same selection scope and reads the task key against the current database.

The plugin uses local STDIO and has no hosted server. Task data returned through the native panel passes through Codex. Your host's data-handling settings and policies apply. Keep database files, transcripts and reference files out of public support reports.

## Update, disable and remove

Keep the previous archive, checksum and extracted marketplace for rollback. Verify the new archive's checksum and extract it into a separate directory. Close the inspector, uninstall the current plugin and replace its marketplace registration:

```sh
codex plugin remove zinn@zinn
codex plugin marketplace remove zinn
codex plugin marketplace add /absolute/path/to/new-release/zinn-codex
```

Install **Zinn** from the new source through Codex's Plugins browser. Restart Codex and start a new chat to use the replacement plugin. Review changed hook definitions again when requested. Keep `codex.json` and `dataDirectory` outside the plugin folder.

Disable **Zinn** in the Plugins browser to stop loading it. Uninstall it there to remove the installed plugin. Remove the marketplace source with:

```sh
codex plugin marketplace remove zinn
```

Your Zinn database, configuration, reference files and selection records remain under your control. Remove the dedicated integration data directory separately if you want to clear its metadata.

To roll back, follow the same replacement steps with the previous extracted marketplace's path and reinstall that plugin version through the Plugins browser. Restart Codex and check lookup, editing and hook trust again. Plugin rollback changes the plugin files. Database compatibility continues to follow the installed CLI and its ordinary [backup and restore rules](/docs/data).

## Troubleshooting

For startup failures, check the configuration path, absolute store path, app `PATH`, Node version and CLI version. Run the configured CLI's `zinn info --json` equivalent with the same `ZINN_DIR` to check database compatibility.

For an empty recent list, check hook trust and `observe`, then mention a real task key in a completed reply or run a direct CLI lookup. Failed verification is reported separately from a missing task. A newly created task becomes available on the next refresh.

If saving fails, keep the panel open, read its error and review the current task before retrying. A retained draft is not proof that the first save failed to reach the database.

## Compatibility

Version 0.1.0 is an Experimental candidate. Native macOS Desktop certification for this candidate is pending. Native support is tied to the exact app, plugin, Node and CLI versions certified for a release.

An earlier candidate's installed-backend check used `codex-cli 0.167.0-alpha.4.1`, Node `26.13.0` and published Zinn CLI `0.44.0` on macOS. It covered startup, task inspection, human field saves, exact inspector assets, persisted plugin disable, removal and reinstall. Backend tests also run on macOS, Linux and Windows. Native panel rendering and hook behavior require their own host checks. Identity command rewriting uses Unix shell syntax.

When the host or plugin version changes, recheck native opening, hook trust, references, human Move and Save attribution, selection after reopen, update, disable, removal and rollback before relying on that combination. Zinn maintains the plugin and its compatibility fixes.

Report problems through [GitHub Issues](https://github.com/yethranayeh/zinn/issues). Include the plugin version and archive checksum, Codex desktop app and CLI versions, Node and Zinn CLI versions, operating system, relevant component settings, expected behavior and a synthetic reproduction. Keep database files, transcripts, reference records and private task text out of the report.
