# Core library

`@zinn-dev/core` provides Zinn's shared operations, input schemas, and SQLite storage. Install it in a Node.js project:

```sh title="Install core"
npm i @zinn-dev/core
```

Core requires Node.js 24.15.0 or newer and also runs on Bun.

Configure the database before the first operation. Supply an explicit actor to every mutation:

```ts title="Configure core and create a project"
import type { Actor } from "@zinn-dev/core";
import { fileURLToPath } from "node:url";
import { configureDatabase, project, task } from "@zinn-dev/core";

configureDatabase({
	client: "example",
	version: "0.1.0",
	executable: fileURLToPath(import.meta.url),
	release: "source",
	allowsLegacyRead: false
});

const actor: Actor = { name: "Alper", email: null, kind: "human" };
const app = project.create({ key: "APP", name: "My project" }, actor);
const createdTask = task.create({ project_id: app.id, title: "Ship the first feature" }, actor);

console.log(createdTask.key); // APP-1
console.log(task.getAll({ projectKey: app.key }));
```

Save the example as `example.ts` and run it with a separate Zinn directory:

```sh title="Run the example in an isolated store"
mkdir -p ./.zinn-example
ZINN_DIR=./.zinn-example node example.ts
```

Core opens the database on first use.

By default it shares `~/.zinn/data/zinn.sqlite` with the CLI, but `ZINN_DIR` and settings files can select another location. See [Settings](/docs/settings) for directory selection.

The client supplies its own `release` identity: `source` for development and `published` for prepared release artifacts. Core identifies its own build independently. Core throws errors while the client handles output, prompts, and optional database-wait and legacy-read callbacks.

## Shared behavior

Names and titles are trimmed and cannot be blank or contain line breaks or control characters.

- Edits change only supplied fields. Valid edits that leave values unchanged preserve modification timestamps and record no activity.
- `task.edit`, `task.label.add`, `task.label.remove` and `task.order` return a `TaskChange`: `{ task, changed }`. The `task` field contains the resulting task, and `changed` is `false` when the requested state was already satisfied. For several label changes, it is `true` when any attachment changed.
- `project.edit`, `column.edit`, `label.edit` and `comment.edit` return `ProjectChange`, `ColumnChange`, `LabelChange` and `CommentChange`: `{ project, changed }`, `{ column, changed }`, `{ label, changed }` and `{ comment, changed }`. The object field contains the resulting record; `changed` is `false` when all supplied values already matched.
- `column.order` also returns a `ColumnChange`. Ordering a task or column to its current position, including before or after itself, returns `changed: false` and records no activity.
- Descriptions default to `null`. Passing `null` or blank text clears them. Non-blank text input keeps its whitespace.
- Descriptions and comment text normalize CRLF line endings to LF, including append, find and replacement inputs. All other whitespace, including lone carriage returns, is preserved.
- Descriptions and comment text are limited to `MAX_TEXT_BYTES`, exported by core: 1 MiB (1,048,576 UTF-8 bytes). Full text is checked before normalization and partial edits check the resulting text. Oversized input fails without writing changes. Editing other fields does not revalidate a stored description.
- Entity mutations record the actor and activity in the same transaction as the change.
- After a change commits, core runs the [hooks](/docs/hooks) from the global settings file in the calling process, with its working directory and environment. `ZINN_HOOKS=0` saves changes without running them.
- Bulk task moves, orders, archives, unarchives and deletes apply in input order and succeed or fail together.
- `task.deleteMany(taskKeys, actor)` returns the deleted tasks in input order, including archived tasks. Task keys must be distinct, ignoring case. Each deletion preserves task activity and records removed relations on the other tasks, including tasks deleted later in the same batch. `task.delete(taskKey, actor)` returns one deleted task.
- `task.orderMany({ taskKeys, direction, targetTaskKey? }, actor)` returns a `TaskChange` per key. It orders the first task as requested, then each next task after the previous one. Multiple tasks must be distinct active tasks in the same project and column. The target cannot be among them. `up` and `down` take one task. A single task ordered before or after itself remains unchanged.

## Activity selection

`activity.getAll` returns full activity records, newest first by timestamp and then event ID. Without a project or task selector it reads across the database.

- `{ taskKey: "APP-1", showDeleted: false }` selects the existing active or archived task. A missing task raises a `CoreError` with kind `missing`; its `facts` identify entity `task` and the requested key.
- `{ taskKey: "APP-1", showDeleted: true }` includes every recoverable existing or deleted task identity sharing that key. Omitting `showDeleted` selects only the existing task, as with `false`.
- `{ taskId: createdTask.id }` selects one exact task identity, including a deleted task. IDs accept full, case-insensitive UUIDs with canonical hyphens or 32 hexadecimal digits. Task ID prefixes are rejected.
- `{ projectKey: "APP" }` selects the existing project's events, its columns, and all its tasks, including archived and explicitly deleted tasks. A missing project raises a `CoreError` with kind `missing`, entity `project`, and the requested key.
- `{ projectKey: "APP", showDeleted: true }` includes every recorded existing or deleted project identity sharing that key. Omitting `showDeleted` or setting it to `false` selects only the existing project.
- `{ projectId: createdProject.id }` selects one exact project identity, including after deletion. Project IDs accept the same full UUID spellings as task IDs, without prefixes.

`projectKey`, `projectId`, `taskKey`, and `taskId` are mutually exclusive. `showDeleted` requires `projectKey` or `taskKey`, including when it is `false`. A valid exact ID or explicit deleted-history query with no recorded matches returns an empty array.

Project selection includes task comments, label attachments, reorders, and original project-deletion snapshots. Global label-definition events are excluded. Cross-project relations include only the selected project's task event and within-project relations include both task events.

Task selection includes original project-deletion events whose snapshots contain the selected task IDs. These events retain their project identity and full payloads. `sessionId` and `threadId` match complete, case-sensitive stored values; all supplied filters must match. `limit` applies after filtering.

`changed` accepts an array of `{ field, value }` filters. The accepted fields are `column`, `priority`, and `labels`. Column and priority match their recorded new values, and labels match a recorded addition. Initial task creation values also match. String values compare case-insensitively, using the names recorded at the time of the event. Use `{ field: "priority", value: null }` to match an unassigned priority on creation or a change that clears it. Column and label values are nonempty strings.

Several values for the same field match any of them. Different fields must all match in the same event. For example, `activity.getAll({ changed: [{ field: "priority", value: "high" }, { field: "labels", value: "bug" }] })` selects events that both set high priority and add bug. Selection and identity filters must also match, and `limit` applies afterwards. The returned records retain their full payloads.

`activity.getTaskIdentities` accepts a task key string or an object containing `taskKey`, `taskId`, and `showDeleted` with the same selection rules. It returns each recoverable task's ID, key, title, and active, archived, or deleted status.

## Database compatibility

`column.inspect({ taskKeys, allowsLegacyRead })` reads existing project column names and requested task identities without creating or upgrading storage. Both are optional. It returns `{ projects: [{ key, columns }], taskKeys }`. Note that task keys that do not identify an existing task are omitted. Empty databases and unacknowledged databases without a schema version return `null` and unavailable storage raises an error.

Opening a database can upgrade it, even for a read operation. Upgrades save a backup first and apply completely or not at all. Upgrades and restores check that foreign keys reference existing tables and rows before committing.

- Older databases upgrade automatically when both the core package and client are published releases, or when `ZINN_DIR` explicitly selects a separate database. Source clients otherwise open older databases read-only until an explicit `migrate.run`.
- Databases newer than core supports open read-only.
- Databases without a schema version are refused unless `allowsLegacyRead` enables best-effort, read-only access.

Core backup and restore operations use the selected store independently of the normal database-opening policy. See [Data and backups](/docs/data) for shared storage and restore behavior.
