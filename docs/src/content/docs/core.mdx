# Core library

`@zinn-dev/core` provides Zinn's shared operations, input schemas, and SQLite storage. Install it in a Node.js project:

```sh title="Install core"
npm i @zinn-dev/core
```

Core requires Node.js 24.15.0 or newer and also runs on Bun.

Configure the database before the first operation. Supply an explicit actor to every mutation:

```ts title="Configure core and create a project"
import type { Actor } from "@zinn-dev/core";
import { fileURLToPath } from "node:url";
import { configureDatabase, project, task } from "@zinn-dev/core";

configureDatabase({
	client: "example",
	version: "0.1.0",
	executable: fileURLToPath(import.meta.url),
	release: "source",
	allowsLegacyRead: false
});

const actor: Actor = { name: "Alper", email: null, kind: "human" };
const app = project.create({ key: "APP", name: "My project" }, actor);
const createdTask = task.create({ project_id: app.id, title: "Ship the first feature" }, actor);

console.log(createdTask.key); // APP-1
console.log(task.getAll({ projectKey: app.key }));
```

Save the example as `example.ts` and run it with a separate Zinn directory:

```sh title="Run the example in an isolated store"
mkdir -p ./.zinn-example
ZINN_DIR=./.zinn-example node example.ts
```

Core opens the database on first use. `project.create` and `label.create` create it when the store has none. Other operations throw a `CoreError` with kind `missing`, entity `database` and the `databasePath`, and create nothing.

By default it shares `~/.zinn/data/zinn.sqlite` with the CLI, but `ZINN_DIR` and settings files can select another location. See [Settings](/docs/settings) for directory selection.

The client supplies its own `release` identity: `source` for development and `published` for prepared release artifacts. Core identifies its own build independently. Core throws errors while the client handles output, prompts, and optional database-wait and legacy-read callbacks.

## Shared behavior

`project.getAllWithTaskCounts()` returns project records with `taskCounts: { active, archived }`. Counts cover existing tasks in each project. Active tasks are unarchived tasks in any column, including Done. Both counts are always present, including zero.

`task.getAll`, `task.search` and `activity.getAll` accept an optional numeric `limit`, an integer from `1` through `11871`, inclusive. The cap applies after all filters and preserves the existing order. Omitting it returns every match. `task.search` counts all hidden archived matches before applying the cap.

`task.getAll({ sort: "activity", limit: 10 })` returns the ten most recently active tasks. Last activity is the newest recorded task event, including comments and relations, or `updated_at` when no events exist. Filters apply before sorting, and the limit applies afterward. Equal times keep board order. Omitting `sort` preserves board order.

`task.getAll` returns an array. `task.getPage` accepts the same task-list filters plus optional `startingAfter` and returns `{ tasks, hasMore }`. Use a task's `id` as the cursor. It accepts a canonical or compact UUID, case-insensitively, or a globally unambiguous left prefix with at least eight hexadecimal digits in either spelling.

The cursor resolves against current tasks globally before list filters. The selected task must match every selection filter. The cursor is excluded, and the next page starts after its current position under the selected sort. Omit `limit` to return every remaining task with `hasMore: false`.

```ts title="Read the next task page"
const firstPage = task.getPage({ projectKey: "APP", limit: 10 });
if (firstPage.hasMore) {
	const nextPage = task.getPage({
		projectKey: "APP",
		limit: 10,
		startingAfter: firstPage.tasks.at(-1)!.id
	});
	console.log(nextPage.tasks);
}
```

Each call reads one current database snapshot. Separate calls do not share a snapshot. Moves, reorders, edits, new activity and other changes can change task positions between pages and cause repeats or skips.

Names and titles are trimmed and cannot be blank or contain line breaks or control characters.

- Edits change only supplied fields. Valid edits that leave values unchanged preserve modification timestamps and record no activity.
- `task.edit`, `task.label.add`, `task.label.remove` and `task.order` return a `TaskChange`: `{ task, changed }`. The `task` field contains the resulting task, and `changed` is `false` when the requested state was already satisfied. For several label changes, it is `true` when any attachment changed.
- `project.edit`, `column.edit`, `label.edit` and `comment.edit` return `ProjectChange`, `ColumnChange`, `LabelChange` and `CommentChange`: `{ project, changed }`, `{ column, changed }`, `{ label, changed }` and `{ comment, changed }`. The object field contains the resulting record; `changed` is `false` when all supplied values already matched.
- `column.order` also returns a `ColumnChange`. Ordering a task or column to its current position, including before or after itself, returns `changed: false` and records no activity.
- `column.getByName(projectKey, columnName)` returns a column matched case-insensitively and throws if the project or column is missing. `column.delete({ projectKey, columnName }, actor)` returns the deleted column and records its project ID, project key and name in activity. It refuses columns holding any active or archived tasks. A project may have no columns. `task.create` then fails with reason `no_columns` without allocating a task number. Add a column with `column.create` before creating tasks.
- Descriptions default to `null`. Passing `null` or blank text clears them. Non-blank text input keeps its whitespace.
- Descriptions and comment text normalize CRLF line endings to LF, including append, find and replacement inputs. All other whitespace, including lone carriage returns, is preserved.
- Descriptions and comment text are limited to `MAX_TEXT_BYTES`, exported by core: 1 MiB (1,048,576 UTF-8 bytes). Full text is checked before normalization and partial edits check the resulting text. Oversized input fails without writing changes. Editing other fields does not revalidate a stored description.
- Entity mutations record the actor and activity in the same transaction as the change.
- After a change commits, core runs the [hooks](/docs/hooks) from the global settings file in the calling process, with its working directory and environment. `ZINN_HOOKS=0` saves changes without running them.
- Bulk task moves, orders, archives, unarchives and deletes apply in input order and succeed or fail together.
- `task.deleteMany(taskKeys, actor)` returns the deleted tasks in input order, including archived tasks. Task keys must be distinct, ignoring case. Each deletion preserves task activity and records removed relations on the other tasks, including tasks deleted later in the same batch. `task.delete(taskKey, actor)` returns one deleted task.
- `project.delete(key, actor)` records aggregate project deletion history and one `relation_delete` event per removed cross-project relation on its surviving task, including archived tasks. Surviving task modification timestamps are preserved.
- `task.orderMany({ taskKeys, direction, targetTaskKey? }, actor)` returns a `TaskChange` per key. It orders the first task as requested, then each next task after the previous one. Multiple tasks must be distinct active tasks in the same project and column. The target cannot be among them. `up` and `down` take one task. A single task ordered before or after itself remains unchanged.

## Task deadlines

Task results include `due_at: number | null`, an exact deadline in integer Unix epoch milliseconds. `task.create` accepts optional `due_at`. Omission or `null` creates an undated task. `task.edit` also accepts `due_at`. Omission preserves the current value and `null` clears it. Repeating the current value or clearing an unset deadline is a no-op that preserves `updated_at` and records no activity.

`timestampSchema`, exported by core, validates integer milliseconds in the JavaScript `Date` range from `-8640000000000000` through `8640000000000000`, inclusive. `activityTimestampSchema` remains exported as an alias to the same schema.

`task.getAll` and `task.search` accept optional `dueSince` and `dueUntil` bounds. Both are inclusive. Use either bound alone or both together. Equal bounds select that exact millisecond, and a reversed range is invalid. A supplied deadline bound excludes tasks whose `due_at` is `null`. Deadline bounds intersect with the other filters before the result limit applies. Search retains its relevance and task-key order.

`task.getAll({ sort: "due" })` sorts by earliest deadline first, puts undated tasks last, and preserves board order for equal deadlines and undated tasks. This is opt-in and does not change task positions. `task.search` has no due sort option.

## Task relations

`relation.create({ sourceTaskKey, targetTaskKey, relation_type }, actor)` creates a relation. Types are `related`, `dependency`, `duplicate` and `subtask`. A pair has at most one relation across all types and both directions. Directed types preserve their source and target. An exact existing relation is an error.

`relation.getConflicts({ sourceTaskKey, targetTaskKey, relation_type })` validates the requested creation and returns conflicting relation records with `source` and `target` task records. Conflicts include a different parent when creating a subtask. Self-relations, exact repeats and subtask cycles fail before confirmation.

After obtaining approval, pass the returned relation IDs as `replace` to authorize exactly those removals:

```ts title="Replace the approved relations"
import { relation } from "@zinn-dev/core";

const request = { sourceTaskKey: "APP-1", targetTaskKey: "APP-2", relation_type: "subtask" as const };
const conflicts = relation.getConflicts(request);
// Obtain approval in the calling interface before replacing these links.
const created = relation.create({ ...request, replace: conflicts.map(({ id }) => id) }, actor);
```

If the conflicting IDs changed before the write, core throws a `CoreError` with kind `conflict` and reason `relation_changed`. `replace: true` explicitly authorizes replacing the current conflicting links without an expected-ID check. Omitting `replace` or passing `false` refuses conflicting links. Every removal and the creation share one transaction and activity timestamp. Failures preserve existing links and activity.

`task.create` accepts `relations: [{ relation_type, targetTaskKey }]`. Identical type and resolved-target requests deduplicate. Different types for one target fail the whole creation without consuming a task number or recording activity.

## Activity selection

`activity.getAll` returns `{ events, hasMore }`. `events` contains full activity records, newest first by timestamp and then event ID. Without a project or task selector it reads across the database. `hasMore` is true only when another event matches after the returned page. Without `limit`, it is false.

Pass `startingAfter` with the last returned event's ID to continue toward older events, excluding that event. It accepts the same full IDs and unique prefixes as `activity.getById`. The cursor event need not match the supplied filters. Every filter applies before the page cap, including `changed`. Omitting `limit` returns every remaining match.

```ts title="Read the next activity page"
const firstPage = activity.getAll({ limit: 10 });
if (firstPage.hasMore) {
	const nextPage = activity.getAll({
		limit: 10,
		startingAfter: firstPage.events.at(-1)!.id
	});
	console.log(nextPage.events);
}
```

Optional numeric `since` and `until` fields filter the stored `created_at`, inclusively, before `limit` applies. Use either bound alone or both together. They accept integer epoch milliseconds between `-8640000000000000` and `8640000000000000`, inclusive. Equal bounds select events at exactly that millisecond. A reversed range raises an input `CoreError` whose `facts.field` is `["until"]`. Historical identity resolution uses the full recorded history before time selection.

- `{ taskKey: "APP-1", showDeleted: false }` selects the existing active or archived task. A missing task raises a `CoreError` with kind `missing`; its `facts` identify entity `task` and the requested key.
- `{ taskKey: "APP-1", showDeleted: true }` includes every recoverable existing or deleted task identity sharing that key. Omitting `showDeleted` selects only the existing task, as with `false`.
- `{ taskId: createdTask.id }` selects one exact task identity, including a deleted task. IDs accept full, case-insensitive UUIDs with canonical hyphens or 32 hexadecimal digits. Task ID prefixes are rejected.
- `{ projectKey: "APP" }` selects the existing project's events, its columns, and all its tasks, including archived and explicitly deleted tasks. A missing project raises a `CoreError` with kind `missing`, entity `project`, and the requested key.
- `{ projectKey: "APP", showDeleted: true }` includes every recorded existing or deleted project identity sharing that key. Omitting `showDeleted` or setting it to `false` selects only the existing project.
- `{ projectId: createdProject.id }` selects one exact project identity, including after deletion. Project IDs accept the same full UUID spellings as task IDs, without prefixes.

`projectKey`, `projectId`, `taskKey`, and `taskId` are mutually exclusive. `showDeleted` requires `projectKey` or `taskKey`, including when it is `false`. A valid exact ID or explicit deleted-history query with no recorded matches returns `{ events: [], hasMore: false }`.

Project selection includes task comments, label attachments, reorders, and original project-deletion snapshots. Global label-definition events are excluded. Cross-project relations include only the selected project's task event and within-project relations include both task events.

Task selection includes original project-deletion events whose snapshots contain the selected task IDs. These events retain their project identity and full payloads. `sessionId` and `threadId` match complete, case-sensitive stored values; all supplied filters must match. `limit` applies after filtering.

`actions` accepts an array of recorded action names, such as `create`, `edit`, `move` or `comment_create`. An event matches any listed action. Action names are case-sensitive and use the `ActivityAction` vocabulary across entity types.

`changed` accepts an array of task field filters. Use `{ field }` to match any change to `column`, `priority`, `labels`, `title` or `description`. Labels match additions and removals. Initial task fields also match, including null priority and description. Initial labels match when at least one label is recorded.

Use `{ field: "due_at" }` to match any recorded deadline change. Do not supply `value` for this field. Task creation snapshots include the initial deadline, including `null` when it is unset. Deadline edits record the previous and new values. Earlier activity payloads retain their recorded shape.

Use `{ field, value }` with `column`, `priority` or `labels` to select recorded new values or added labels. Initial values on task creation also match. String values compare case-insensitively, using the names recorded at the time of the event. Use `{ field: "priority", value: null }` to match an unassigned priority on creation or a change that clears it. String values must be nonempty.

Several filters for the same field match any of them, including a value-free filter alongside one with a value. Different fields must all match in the same event. For example, `activity.getAll({ actions: ["edit"], changed: [{ field: "description" }, { field: "priority", value: "high" }] })` selects edits that change the description and set high priority. Selection and identity filters must also match, and `limit` applies afterwards. The returned records retain their full payloads.

`activity.getTaskIdentities` accepts a task key string or an object containing `taskKey`, `taskId`, and `showDeleted` with the same selection rules. It returns each recoverable task's ID, key, title, and active, archived, or deleted status.

## SQLite errors

SQLite failures throw `SqliteError` on both Node.js and Bun. Its `code` is a symbolic name, `errcode` is the numeric extended result code, and `cause` retains the original driver error.

Use `isSqliteErrorCode(error, "SQLITE_BUSY")` for an exact result code and `isSqliteErrorFamily(error, "SQLITE_BUSY")` for the primary code and all its subtypes. For example, `SQLITE_BUSY_SNAPSHOT` matches the **BUSY** family but does not exactly match `SQLITE_BUSY`. The exported `SqliteCode` and `SqlitePrimaryCode` types provide the accepted names.

Both helpers accept `unknown`, narrow matching values to `SqliteError`, and inspect only that error. They do not inspect its cause. An unlisted extended code matches its known primary family. Its `code` falls back to the primary name for display, while exact matching still distinguishes it from the primary result code. A wholly unknown primary code displays as `SQLITE_ERROR` and matches neither helper.

## Database compatibility

`column.inspect({ taskKeys, allowsLegacyRead })` reads existing project column names and requested task identities without creating or upgrading storage. Both are optional. It returns `{ projects: [{ key, columns }], taskKeys }`. Note that task keys that do not identify an existing task are omitted. Empty databases and unacknowledged databases without a schema version return `null` and unavailable storage raises an error.

Opening a database can upgrade it, even for a read operation. Upgrades save a backup first and apply completely or not at all. Upgrades and restores check that foreign keys reference existing tables and rows before committing.

Each migration step also checks existing foreign-key definitions, including those in tables it does not rebuild. An unexpected change rolls back the upgrade. Intentional changes must match the migration's declared starting and resulting definitions.

- Older databases upgrade automatically when both the core package and client are published releases, or when `ZINN_DIR` explicitly selects a separate database. Source clients otherwise open older databases read-only until an explicit `migrate.run`.
- Databases newer than core supports open read-only.
- Databases without a schema version are refused unless `allowsLegacyRead` enables best-effort, read-only access.

Core backup and restore operations use the selected store independently of the normal database-opening policy. See [Data and backups](/docs/data) for shared storage and restore behavior.
