# Reading and pagination

## Project counts

`project.getAllWithTaskCounts()` returns project records with `taskCounts: { active, archived }`. Counts cover existing tasks in each project. Active tasks are unarchived tasks in any column, including Done. Both counts are always present, including zero.

## List and filter tasks

`task.getAll`, `task.search` and `activity.getAll` accept an optional numeric `limit`, an integer from `1` through `Number.MAX_SAFE_INTEGER`, inclusive. The cap applies after all filters and preserves the existing order. Omitting it returns every match. `task.search` counts all hidden archived matches before applying the cap.

### Sort by activity

`task.getAll({ sort: "activity", limit: 10 })` returns the ten most recently active tasks. Last activity is the newest recorded task event, including comments and relations, or `updated_at` when no events exist. Filters apply before sorting, and the limit applies afterward. Equal times keep board order. Omitting `sort` preserves board order.

## Page through tasks

`task.getAll` returns an array. `task.getPage` accepts the same task-list filters plus optional `startingAfter` and returns `{ tasks, hasMore, nextCursor? }`. `nextCursor` is an opaque token, present only when `hasMore` is true. Pass it as `startingAfter` to continue.

Both take `state`: `"open"`, `"closed"` or `"all"` (the default). A task is closed when its column's category is `done` or `cancelled`. `state` combines with `archive` and every other filter.

Continuation survives edits, moves, archiving, relabelling, deadline changes and deletion of the last listed task. Filters may change while the sort stays the same. No snapshot is kept between calls, so other tasks changing in between can still cause repeats or skips. The order breaks remaining ties by task ID. Omit `limit` to return every remaining task with `hasMore: false`.

A refused cursor throws a `CoreError` with kind `input` and `field: ["startingAfter"]`. The `reason` is `invalid_cursor` (malformed), `cursor_version` (made by another version), `different_sort` (made for another sort) or `task_id_cursor` (a task ID).

The example below extends [Core setup](/docs/core#configure-the-library). Keep its database configuration and `task` import in the same process, and run with its isolated `ZINN_DIR`.

```ts title="Read the next task page"
const firstPage = task.getPage({ projectKey: "APP", limit: 10 });
if (firstPage.hasMore) {
	const nextPage = task.getPage({
		projectKey: "APP",
		limit: 10,
		startingAfter: firstPage.nextCursor
	});
	console.log(nextPage.tasks);
}
```

Each call reads one current database snapshot. Separate calls do not share a snapshot. Moves, reorders, edits, new activity and other changes can change task positions between pages and cause repeats or skips.

## Next ready task

`task.next({ projectKey?, columnName? })` returns the next ready task, or `null` when none is ready. A task is ready when it is active, in a column whose category is `todo` or `backlog`, has no live [claim](/docs/core/writing#task-claims), and every task it depends on is archived or in a column whose category is `done` or `cancelled`. A task with a live claim is never returned, whoever holds it. Ready tasks in `todo` columns come first, then those in `backlog` columns. Within each, they are ordered by priority (urgent first, unset last), then the earliest `due_at` with undated tasks last, then creation time. `columnName` takes ready tasks from that one column instead, of any category but `done` and `cancelled`. It matches by exact name, ignoring case, as in `task.getAll`. On an older database opened read-only, which has no categories, every column but a board's last holds ready tasks, and no task has a claim. An unknown `projectKey` throws a `CoreError` with kind `missing`.

## Filter and sort by deadline

`task.getAll` and `task.search` accept optional `dueSince` and `dueUntil` bounds. Both are inclusive. Use either bound alone or both together. Equal bounds select that exact millisecond, and a reversed range is invalid. A supplied deadline bound excludes tasks whose `due_at` is `null`. Deadline bounds intersect with the other filters before the result limit applies. Search retains its relevance and task-key order.

`task.getAll({ sort: "due" })` sorts by earliest deadline first, puts undated tasks last, and preserves board order for equal deadlines and undated tasks. This is opt-in and does not change task positions. `task.search` has no due sort option.
