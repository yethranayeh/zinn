# Storage, compatibility and errors

## Open the database

Core opens the database on first use. `project.create` and `label.create` create it when the store has none. Other operations throw a `CoreError` with kind `missing`, entity `database` and the `databasePath`, and create nothing.

By default it shares `~/.zinn/data/zinn.sqlite` with the CLI, but `ZINN_DIR` and settings files can select another location. See [Settings](/docs/settings) for directory selection.

## Capture storage destinations

`getStorage()` returns a fresh `Storage` snapshot on each call. Settings and the selected directory are chosen on first use and stay cached. Each snapshot resolves the database destination through the current filesystem links. `getBackupStorage()` resolves the backup folder as well, for an operation that writes a backup. Keep one snapshot throughout an operation. An existing connection retains the destination it opened, including for its errors and search reindexing.

## Client release identity

The client supplies its own `release` identity: `source` for development and `published` for prepared release artifacts. Core identifies its own build independently. Core throws errors while the client handles output, prompts, and an optional database-wait callback.

## SQLite errors

SQLite failures throw `SqliteError` on both Node.js and Bun. Its `code` is a symbolic name, `errcode` is the numeric extended result code, and `cause` retains the original driver error.

Use `isSqliteErrorCode(error, "SQLITE_BUSY")` for an exact result code and `isSqliteErrorFamily(error, "SQLITE_BUSY")` for the primary code and all its subtypes. For example, `SQLITE_BUSY_SNAPSHOT` matches the **BUSY** family but does not exactly match `SQLITE_BUSY`. The exported `SqliteCode` and `SqlitePrimaryCode` types provide the accepted names.

Both helpers accept `unknown`, narrow matching values to `SqliteError`, and inspect only that error. They do not inspect its cause. An unlisted extended code matches its known primary family. Its `code` falls back to the primary name for display, while exact matching still distinguishes it from the primary result code. A wholly unknown primary code displays as `SQLITE_ERROR` and matches neither helper.

## Database compatibility

`column.inspect({ taskKeys })` reads existing project column names and requested task identities without creating or upgrading storage. `taskKeys` is optional. It returns `{ projects: [{ key, columns }], taskKeys }`. Note that task keys that do not identify an existing task are omitted. Empty databases and databases without a schema version return `null` and unavailable storage raises an error.

Opening a database can upgrade it, even for a read operation. Upgrades save a backup first and apply completely or not at all. Upgrades and restores check that foreign keys reference existing tables and rows before committing.

Each migration step also checks existing foreign-key definitions, including those in tables it does not rebuild. An unexpected change rolls back the upgrade. Intentional changes must match the migration's declared starting and resulting definitions.

- Older databases upgrade automatically when both the core package and client are published releases, or when `ZINN_DIR` explicitly selects a separate database. Source clients otherwise open older databases read-only until an explicit `migrate.run`.
- If an automatic upgrade saves a backup and then fails or is interrupted before committing, later automatic opens throw a `CoreError` with kind `conflict` and reason `migration_paused`. Call `migrate.run` to retry. A successful migration or restore clears the pause.
- Databases newer than core supports open read-only.
- Databases without a schema version are refused.
- A process that keeps the database open checks the schema version at the start of each write. When another process has changed it, such as a newer Zinn upgrading the database, the write throws a `CoreError` with kind `conflict` and reason `newer_database` or `older_database` and changes nothing. Reads keep working. Restart the process to write again.

Core backup and restore operations use the selected store independently of the normal database-opening policy. See [Data and backups](/docs/data) for shared storage and restore behavior.

## Restore to a captured destination

`backup.restore({ path, client, version, storage? })` accepts an optional `BackupStorage` snapshot from `getBackupStorage()`. Pass it when the caller confirms a destination before restoring. Restore uses that captured destination even if the configured symbolic link changes afterward. Without `storage`, restore captures a fresh snapshot when called. Source backups are validated again when restore runs.
