### Added

- `task claim <task-key> --lease <duration>` marks a task as being worked on by you for a lease from `1m` through `24h`, so other agents and people can see who works on it. A claim is advisory and kept apart from the task's column. `task next` skips a task with a live claim. `task heartbeat` renews your claim, and `task release` removes it. Any change you make to the task renews it too, and a claim expires when its lease runs out or 24 hours after your last change to the task. `--force` takes over someone else's live claim, and an expired claim is replaced. Agents are told apart by their session, so an agent needs `ZINN_SESSION_ID`, or a session ID its host provides. Archiving a task or moving it into a done or cancelled column releases its claim. Every task object in `--json` output and every task core returns has a `claim` field, `null` without a claim. Claim refusals fail with error code `conflict` and the new reasons `claimed`, `not_claimed` and `claim_limit`, with the claim's expiry in the new `claimExpiresAt` error detail. Hooks and activity get the new actions `claim`, `claim_take`, `claim_heartbeat` and `claim_release`. Core adds `task.claim`, `task.heartbeat` and `task.release`. See [CLI](/docs/cli#claim-tasks), [Scripting](/docs/scripting#entity-identity) and [Core](/docs/core#task-claims).
- `task next` shows the next task that is ready to work on: active, in a todo or backlog column, and with every task it depends on archived or in a done or cancelled column. Todo tasks come before backlog tasks, then tasks are ordered by priority, the earliest deadline and the oldest task. `--column` takes ready tasks from one column instead, in any category except done or cancelled. A task with a live claim is skipped, whoever holds it, so `--column` on the working column finds in-progress work with no live claim. With nothing ready, it exits `0`, and `--json` prints `null`. Core gains `task.next`. The bundled workflow skill now teaches picking up work with `task next`, taking a task with `task move --from`, claiming it with `task claim`, renewing and releasing the claim, recovering abandoned work through `task next --column`, and finding the working and review columns by their category. See [CLI](/docs/cli#next-ready-task).
- Edit commands take the values read before the edit. `task edit` takes `--expect-title`, `--expect-description`, `--expect-description-file`, `--expect-priority` and `--expect-due`. `task comment edit` takes `--expect-text` and `--expect-text-file`. `project edit` takes `--expect-name`, `--expect-description` and `--expect-description-file`. `label edit` takes `--expect-name`, `--expect-description`, `--expect-description-file` and `--expect-color`. When a stored value differs, nothing changes and the command fails with error code `conflict`, reason `value_changed`, and the new `changedFields` error detail naming the fields that differ. Of several agents editing the same task, comment, project or label from the same values, exactly one succeeds. Core's `task.edit`, `comment.edit`, `project.edit` and `label.edit` take the same check as `expected`. See [CLI](/docs/cli#edit-tasks).
- `task move --from <column>` moves tasks only if they are still in that column. Otherwise nothing changes and the command fails with error code `conflict`, reason `column_changed`, and the new `expectedColumn` and `actualColumn` error details. Of several agents taking the same task this way, exactly one succeeds. Core's `task.move` and `task.moveMany` take the same check as `fromColumn`. See [CLI](/docs/cli#move-and-order-tasks).
- `task list --state open` lists only tasks outside done and cancelled columns, and `--state closed` lists only tasks in them. `--state all` is the default. A column's category decides its state. In core, `task.getAll` and `task.getPage` take a `state` option with the same values. See [CLI](/docs/cli).
- `activity list --follow` prints activity as any client commits it and runs until stopped. It prints only events committed after it starts, applies the other `activity list` filters, and with `--json` prints one record per line. It cannot be used with `--limit` or `--starting-after`. The core library adds `activity.follow` without pagination inputs, and `zinn capabilities --json` describes the stream with the new result mode `json-lines`. See [CLI](/docs/cli#activity), [Scripting](/docs/scripting#discover-the-command-contract) and [Core](/docs/core#activity-selection).
- `zinn doctor` checks the settings, store folder, database, search index and installed agent skill for problems and suggests a fix for each. It changes nothing. It exits with code 1 when any check reports a warning or problem, and prints the checks on stdout either way. In `zinn capabilities --json`, its result carries `findingsExitCode: 1` beside `exitCode: 0`. See [Check for problems](/docs/cli#check-for-problems).
- `zinn skill install` installs the agent skill bundled with the installed CLI for every agent, through the [skills CLI](https://github.com/vercel-labs/skills). The installed skill matches the CLI version. Rerun it after upgrading Zinn. When the skills CLI fails, `zinn skill install` exits with its exit code, which `--json` errors carry in `error.details.exitCode`. With `--json`, the skills CLI's output is reported as notices. The bundled skill no longer asks agents to compare versions with the npm registry or GitHub. When the CLI lacks a command the skill uses, the agent points the user to `zinn skill install`. See [Agent skill](/docs/cli#agent-skill).
- The `busyTimeoutMs` setting sets how long a command waits, in milliseconds, for another Zinn process to finish writing before it fails as busy. It defaults to `30000`, and `0` fails at once. See [Settings](/docs/settings#wait-for-a-busy-database).
- `update` is an alias for `edit`, in every command that has one, as in `zinn task update APP-1 --priority high`. See [CLI](/docs/cli#command-aliases).

### Changed

- **Breaking CLI and core API:** every column has a category: `backlog`, `todo`, `in_progress`, `review`, `done` or `cancelled`. It says how Zinn treats a column's tasks, whatever the column is called or where it sits, so renaming or moving a column keeps its category. Tasks in `done` and `cancelled` columns are closed. `project column create` now requires `--category`, and core's `column.create` requires `category`: add it to scripts that create columns. `project column edit` and `column.edit` take `--category` or `category`, and changing the category of a column that holds tasks asks for confirmation (`--yes`). Column names are colored by category instead of by position: backlog and cancelled gray, in progress blue, review yellow, done green, and todo uncolored. `project column list` and `project view` show each column's category, column results in `--json` add `category`, and task results add `column_category`. New projects start with Backlog, TODO, Doing, Review, Done and Cancelled. The upgrade gives existing columns a category from their names: Backlog, TODO, In Progress, Doing, Review, Done and Cancelled take the matching category, and any other column becomes `todo`. Existing projects keep their columns. See [CLI](/docs/cli#start-a-project).
- **Schema version 6:** the schema adds the task claim table. A published release upgrades an existing database on first use, after saving a backup, and `zinn migrate` runs the upgrade on request. An older Zinn can read the upgraded database but refuses changes to it.
- A process that keeps the database open refuses its next change when another process has changed the database's schema version since it opened, and leaves the database as it was. Reads keep working. Restart Zinn to write again. Through core the write throws a `CoreError` with kind `conflict`. See [Core](/docs/core#database-compatibility).

### Removed

- **Breaking CLI and core API:** `--allow-legacy-read` is removed, and core's `configureDatabase` no longer takes `allowsLegacyRead` or `onLegacyRead`. Remove the flag from scripts and the options from core calls. A database without a schema version is refused, while a database from a released version stays readable.

### Fixed

- When a transaction fails and its `ROLLBACK` fails too, the connection now refuses every later statement and transaction until it is closed. Before, a later write on that connection could report success and then be lost when the connection closed. The rollback error stays attached to the original error.
- `zinn restore` checks the backup file again once it holds the write lock. A backup deleted, replaced or overwritten after the first check is now refused, and the database is left as it was. Before, a deleted backup could leave the database empty while the restore reported success. Restore also refuses a backup path that leads to the database itself, without waiting for the lock. See [Data](/docs/data#restore-a-database).
